# FNOS-001 批量真机验收记录

本记录汇总[批量真机验收规程](/testing/FNOS-001-batch-verification)跑出的结果。判定口径、通道等效性
与设备清理纪律见该规程；单应用用例见 [FNOS-001 测试用例集](/testing/FNOS-001-test-cases)。

**敏感信息**：设备地址、账号、口令、令牌一律不入本记录，命令示例用 `${FNOS_HOST}` 占位。

## 1. 验收范围与方法

| 项 | 值 |
| --- | --- |
| 通道 | Midscene 驱动 fnOS 应用中心 Web UI（设备端 `appcenter-cli` 因 rpcbroker 权限不可用） |
| 范围 | 仓库内全部可转换 Docker 应用，**排除目标设备上已安装的用户既有应用**（避免动用户环境） |
| 单应用流程 | 构建 → 上传 → 解析 → 填参 → 安装 → 等 `running` → 入口探测 → 卸载（删数据）→ 清理残留 → 取失败日志 |
| 判定分级 | `PASS` / `FAIL` / `BLOCKED` / `UNVERIFIED` / `BUILD_FAIL` |
| 产物 | `scripts/batch-verify.mjs`（设备地址与账号走环境变量，不入库） |

## 3. 本轮确认的系统性缺陷

### 3.1 卸载「删除所有数据」实际删不掉，且日志谎报成功

**现象**：卸载选择「删除所有数据」后，应用中心提示卸载完成、桌面图标消失、端口释放，但
`/vol2/@appdata/<app>` 与 `/vol2/@apphome/<app>` 仍在设备上。

**根因（实测取证）**：

| 项 | 实测值 |
| --- | --- |
| 卸载回调执行身份 | 包用户（`uid=969`，`groups=964`），`TRIM_RUN_USERNAME` 与 `TRIM_USERNAME` 相同 |
| 目标目录 | `/vol2/@appdata/<app>`，属主就是该包用户，mode `770` |
| 失败原因 | 删除目录项需要对**父目录** `/vol2/@appdata`、`/vol2/@apphome`（`root:root`，`755`）有写权限；包用户没有 |
| 实际报错 | `rm: cannot remove '/vol2/@appdata/<app>': Permission denied` |
| 脚本行为 | 仍无条件打印「Application data deleted.」并 `exit 0` —— **用户看到删除成功，目录其实还在** |

**影响面**：仓库内全部使用该写法的应用。

**候选修法**（未实施，待决策）：

1. 生命周期脚本改 Root 模式（官方权限文档允许「访问包用户无法处理的文件」），再用 `runuser`
   把服务进程切回包用户 —— 但会改动 `run-as` 模型，须评估对 04-AC-04（应用以 `docker-<app>` 用户运行）的影响；
2. 回调只删目录**内容**（属主自己，`rwx` 允许删除内部条目），目录壳残留并**如实上报**，不再谎报成功；
3. 申请平台提供应用数据清理机制。

**三组决定性实测**（2026-10-20，用于确定「到底需不需要 Root 模式」）：

| 实验 | 做法 | 结果 | 推论 |
| --- | --- | --- | --- |
| ① 平台是否原生删数据 | 把卸载回调改成**空操作**再卸载 | 数据目录**仍在**；但回调**确实被调用** | **平台不删数据**，删除责任在应用侧 |
| ② 只删内容能否删干净 | 回调只 `rm -rf "$DIR"/*`，以会写真实数据的应用测试 | **删不干净**：容器以 root 写入的文件（实测 `storage/app/.gitignore`）报 `Permission denied` | 包用户能删自己拥有的目录项，删不动 **root 属主**的文件 |
| ③ 包用户能否自行提权 | 回调内 `runuser -u "$TRIM_USERNAME" -- rm -rf ...` | `runuser: may not be used by non-root users` | 包用户无法自行提权 |

补充事实：存储卷为 btrfs + `trimacl`；`/vol2/@appdata`、`/vol2/@apphome` 属 `root:root` `755`；
**uid ≥ 1000 的普通账号在该卷上能 unlink 条目，uid 9xx 的服务账号（包用户）不行**——平台对「人类账号」
与「服务账号」的权限并不对等。

### 2026-10-21 定案与实施

用户裁定：**「应用可以删除自己创建的数据，但不允许删除环境变量对应的目录。」**

据此的实施（已落地并真机验证）：

| 项 | 落地内容 |
| --- | --- |
| 回调写法 | 全部 **179 个转换应用**的 `cmd/uninstall_callback` 统一为「只删内容 + 逐目录如实上报」；不再 unlink 平台目录；删不干净时输出「could not be removed」而**不是**「deleted」 |
| Root 模式 | **不引入**。删不掉的根因是「文件不是包用户自己创建的」，解法是让容器以包用户身份写数据（`user: "${TRIM_UID}:${TRIM_GID}"`），或对镜像固定 uid 的应用在 `install_callback` 里用 ACL 授权（含默认 ACL） |
| 用户既有应用 | `831b7d3` 之前的 **14 个**按禁止项 8 不修改 |
| 真机验证 | `fn-it-tools`：装好 → 入口 200 → 卸载选「删除所有数据」→ 日志输出 `Application data deleted: /vol2/@appdata/fn-it-tools` 与 `.../fn-it-tools`；设备核对：两个平台目录**仍在**、**内容条目数 0**（平台保留目录、应用只删内容） |
| 批量验收残留 | 验收器仍用有权限的账号清理目录壳，保证设备不被测试污染 |

### 同期发现的独立问题（与删除无关，单独跟踪）

`fn-2fauth` 安装后状态 `running`、端口 8000 有响应，但**应用返回 HTTP 500**（`{"message":"Server Error"}`）。
取证：`php-fpm` 以 uid 1000 在跑，容器确实活着；`cmd/main` 的 `status` 却报「container is NOT running」，
两者矛盾。该问题属应用自身/属主/向导默认值的范畴，**与卸载删除无关**，已单列为待查项，不计入删除缺陷。

### 3.2 卸载阶段的日志噪声会掩盖真实失败原因

卸载时 `cmd/main` 被再次调用，此时应用目录已被框架移除，日志出现
`exit status 1: open /docker/docker-compose.yaml: no such file or directory`。这是**卸载阶段的正常噪声**，
判断失败原因必须看它**之前**的输出。

## 4. 失败形态分类与处置

| 形态 | 判定 | 处置 |
| --- | --- | --- |
| 向导必填项无法自动填写（如站点访问地址、真实密钥） | `UNVERIFIED` | 人工补齐后单测；不算转换缺陷 |
| 需要外部数据库/中间件（`DB_HOST`/`REDIS_HOST` 等已填本地默认） | `BLOCKED` | 环境不具备；不算转换缺陷 |
| 安装后端口未响应，但容器在运行 | 首次安装多为**镜像拉取耗时**（探针窗口不足） | 镜像已缓存后二次复测；仍失败则取容器日志定位 |
| 应用返回 5xx | `FAIL` | 取应用自身日志；需排除历史残留数据影响 |
| 端口映射错误 | 本轮**未发现** | 批量比对「应用中心服务端口」与向导 `APP_PORT`，**全部一致** |
