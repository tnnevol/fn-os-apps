# FNOS-001 批量真机验收规程

本规程规定**批量**验证转换应用能否正常安装、启动、打开的标准流程。它与
[单应用测试用例集](/testing/FNOS-001-test-cases) 的分工是：用例集定义「怎么测、什么算通过」，
本规程定义「怎么把这套用例跑遍全部应用并留下可复核证据」。

## 1. 为什么需要批量通道

设备端 `appcenter-cli` 在多数目标设备上因 `/run/trim_app_cgi/rpcbroker` 权限直接 panic，
无法批量安装；逐个在应用中心 UI 手工安装也不具备可重复性与可留证性。因此批量验收走
**Midscene 驱动 fnOS 应用中心 Web UI**：复用已登录的真实浏览器会话，用应用中心自身的
HTTP 接口完成安装、启动、卸载，并把 UI 通道与设备端 CLI 通道的结论**等效**对待。

| 通道 | 工具 | 适用 | 限制 |
| --- | --- | --- | --- |
| 设备端 CLI | `appcenter-cli` | 目标设备上直接安装与检查 | 需要设备侧 RPC 权限，权限不足时启动即 panic |
| Web UI 自动化 | Midscene（`@midscene/web`，Bridge 模式） | `appcenter-cli` 不可用时，复用用户已登录的 Chrome 走应用中心 | 只能观察接口返回与设备状态，不能直接读容器日志 |

两条通道**不改变判定口径**：结论必须落到「设备上发生了什么」，不能由本地构建结果代替。

## 2. 环境准备

| 项 | 说明 |
| --- | --- |
| 浏览器 | 用户本人已登录 fnOS 的 Chrome，并安装 Midscene 扩展 |
| 桥配置 | 由 DSH 本地桥提供的固定四行（`curl /v1/midscene-env` 取），**不涉及任何第三方模型密钥** |
| 设备通道 | SSH 可读 `/var/log/apps/<app>.log`（应用生命周期日志）与 `/vol2/@appdata`、`/vol2/@apphome` |
| 暂存目录 | 设备上一个应用中心可见的目录（用于「以 NAS 路径安装」，免去逐个文件上传） |

**设备地址、SSH 账号、口令、令牌一律由环境变量传入，不写进任何文档、脚本或结果文件。**
文档中设备一律以「目标测试设备」指代，命令示例用 `${FNOS_HOST}` 占位。

## 3. 单应用流程（每个应用都走完这七步）

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 本地 `fnpack build` | 产出 `.fpk`；失败记 `BUILD_FAIL` |
| 2 | 把 `.fpk` 放到设备暂存目录 | — |
| 3 | 应用中心解析安装包（`packageSourceType=file` + `path`） | 解析成功、拿到 `appName` 与 `version` |
| 4 | 读取安装向导 schema 并自动填参 | 必填项全部可填；否则记 `UNVERIFIED` |
| 5 | 提交安装任务并轮询到终态 | 安装任务成功；否则记 `FAIL` 或 `BLOCKED` |
| 6 | 等待应用进入 `running`，再探测入口端口 | **顺序不可颠倒**：先卸会导致端口已关闭，探针必然失败 |
| 7 | 卸载（选「删除所有数据」）→ 清理残留目录 → 取失败日志 | 卸载后设备上不得留下该应用 |

### 3.1 向导自动填参规则

| 字段类型 | 处理 |
| --- | --- |
| 端口（`initValue` 合法） | 用应用自带默认值，保持「测的就是发布配置」 |
| `password` / 密钥类 | 生成随机值；**长度按 `helpText` 写明的位数**（如「32 位随机字符串」），否则服务端会拒绝 |
| 文本类且带 `rules[].pattern` | 用 `initValue` 先过一遍正则，不通过则记 `UNVERIFIED` |
| 必填但无默认值、且不是密钥 | 记 `UNVERIFIED`，不猜值 |

**必填项无法自动填写时必须记 `UNVERIFIED` 而不是猜一个值**——猜出来的值会让「装上了」失去意义。

### 3.2 入口探测

- 入口地址取应用中心返回的 `appServiceInfo.urls.port`，拼 `http://${FNOS_HOST}:<port>/`。
- **应用中心报 `running` 不等于容器已在监听**：探针要重试若干次再下结论，否则会把「启动慢」误判成 FAIL。
- 判定可访问的 HTTP 码：`200 / 301 / 302 / 303 / 307 / 401 / 403`。`000`（连接失败）视为不可访问。

## 4. 判定分级

| 判定 | 含义 | 计入转换缺陷 |
| --- | --- | --- |
| `PASS` | 安装成功 + `running` + 入口可访问 | — |
| `FAIL` | 安装或启动失败，且日志指向转换自身的问题 | ✅ |
| `BLOCKED` | 依赖外部数据库/中间件、端口被占用等环境原因 | ❌ |
| `UNVERIFIED` | 向导必填项无法自动填写，需人工确认 | ❌ |
| `BUILD_FAIL` | 本地 `fnpack build` 失败 | ✅ |

**红线**（与 FNOS-001-04-AC-06 一致）：不得出现「安装成功且显示运行中，但实际不可访问」。
端口被占用时，允许的两种表现是：向导表单阶段拦截，或应用中心显示未运行。

## 5. 失败取证

| 场景 | 取证方式 |
| --- | --- |
| 安装/启动失败 | SSH 读 `/var/log/apps/<app>.log` 尾部（生命周期脚本的 stdout/stderr 汇总） |
| 入口不可访问 | 同上 + 应用中心返回的 `status` 与 `appServiceInfo` |
| 卸载后残留 | 查 `/vol2/@appdata/<app>`、`/vol2/@apphome/<app>` 是否仍在 |

日志读取不需要提权：应用生命周期日志对普通账号可读。**日志里出现 `exit status 1: open
/docker/docker-compose.yaml` 是卸载阶段的正常噪声**（应用目录已被框架移除），判断失败原因要
看它**之前**的输出。

## 6. 设备清理纪律

批量验收会反复在设备上装卸应用，必须保证：

1. **逐个测试、逐个卸载**，不在设备上堆积多个测试应用；
2. 卸载后核对三项：桌面入口图标消失、入口端口不再服务（`curl` 返回 `000`）、应用中心列表中无该应用；
3. **清理数据目录残留**：应用卸载回调可能删不掉自己的数据目录（见
   [转换规约的待确认项](/development/1panel-conversion)），需由有权限的账号清掉，
   否则设备上会堆积空目录；
4. 暂存目录里的 `.fpk` 用完即删。

## 7. 证据与可复核性

- 批量结果以 JSON Lines 逐条落盘，**每个应用一条**，中途崩溃不丢已完成部分；
- 每条记录含：应用名、判定、阶段、应用状态、入口地址与 HTTP 码、卸载结果、残留计数、
  失败时的日志尾部；
- 结论进 [真实环境验收记录](/validation/README)，未执行的验收条件保持「未执行」。

## 8. 已知限制

| 限制 | 说明 |
| --- | --- |
| 桥连接会被回收 | 浏览器扩展后台休眠会让传输断开；状态必须存在验收器侧，断线只重连重试当前步 |
| 单次桥调用上限 30 秒 | 耗时的安装轮询必须由验收器侧反复短调用，不能塞进一次调用 |
| 只观察接口与设备状态 | 拿不到容器内部状态；容器级取证仍需设备端 CLI 或 `docker` 权限 |
| 向导必填项 | 无法自动填写的应用只能记 `UNVERIFIED`，需人工补齐后再单测 |
